A consolidated implementation guide for anyone _writing a ddot.it parser_ (a "reader" in ddot.it
terminology). It walks the prose specification, the formal grammar and the golden test corpus in
the order an implementer needs them, and says what each one settles.

[NOTE]
====
This document is *derived*. Two sources are normative and win over anything said here:

. the link:../site/spec/ddot-it-parse.adoc[Parse Specification] — syntax, semantics, and the
  link:../site/spec/ddot-it-parse.adoc#events[triple event] wire format;
. the golden corpus at link:../test-data/cases/[`test-data/cases/`] — the byte-exact contract.

Where they appear to disagree, the corpus is the tiebreaker for *what a conforming
implementation emits*, and the specification is the tiebreaker for *why*. Written against Parse
Specification 1.2.0 / language version 1.3.

[[smallest-model]]
== TL;DR: the smallest model required to parse ddot.it

*A regular language / finite-state machine is sufficient. You do not need a context-free grammar,
a stack, recursion, backtracking, or unbounded lookahead.*

More precisely, ddot.it is parsed by a *line-oriented deterministic finite-state transducer*:

* *Structural class (Chomsky hierarchy): Type-3 (regular).* There is no nested or recursive
  construct anywhere in the language. Metadata blocks do not nest; `!!off`/`!!on` regions toggle
  rather than nest; `!!block` bodies are flat; there are no balanced brackets.

* *Per-line lexing is a plain regular expression* over a five-token alphabet plus text — see
  <<lexing>>.

* *The only cross-line memory is a fixed set of modes plus a couple of string registers.* The
  modes are `normal`, `in-meta-block`, `excluded` and `in-block`. The registers hold *data copied
  verbatim* — the current subject (for <<inheritance,subject inheritance>>) and the active
  block's end-marker string. Because these registers are copied, not matched structurally, they
  do not raise the language above regular. In automata terms this is a *finite-state transducer
  with registers* (a streaming string transducer), strictly weaker than a pushdown automaton.

* *Objects may themselves contain `..`.* Only the `..`/`....` that delimit a triple's slots are
  operators; the object runs to end of line and is taken verbatim, so `a ..path.. ../../foo.txt`
  is legal (object `../../foo.txt`). This is still regular — the object is just `.*$`. See
  <<object-literal>>.

* *Lookahead:* one token, in exactly one place. A line-initial `,,` is a
  <<meta-block,meta-block opener>> only if a newline follows it; otherwise it is the start of a
  subject. Nothing else needs to look ahead.

.Practical consequence
[TIP]
====
You can implement a fully conforming ddot.it parser as:

[source,text]
----
for each line (after newline normalisation):
    dispatch on mode (in-block / excluded / in-meta-block / normal)
    find at most two operators; split off the first ',,'
    emit / accumulate
----

No parser generator, no grammar runtime, no recursion. A hand-written loop with four state
variables is the reference design — see <<algorithm>>. The smallest *correct* procedure is
written out separately in link:parsing-procedure.adoc[Minimum Parsing Procedure].
====

[[single-regex]]
== Can a single multi-line regex parse ddot.it?

*Almost — but not fully, and the gap is instructive.* A single multi-line (DOTALL) regex, applied
*globally* (iterated over matches), can *segment* the document — matching one
triple-with-metadata, or one block, per match. But it cannot *emit correct events on its own*,
because two things need memory that a regex match does not carry between matches.

=== What one regex *can* match in a single pattern

Using alternation, `(?s)` (dotall) and `(?m)` (multiline), a single pattern can recognise, per
match:

* a full *typed / untyped triple* plus its *inline* meta and its *trailing `,,` … `,,` block* —
  the object runs to end-of-line, so the <<object-literal,`..`-in-object>> rule is just `.*$`;
* a *`!!block` body with a custom `?end=` marker*, via a *named backreference* — `\k<end>` — so
  the dynamic closing delimiter is handled *inside one match* (PCRE, Java, and JS/ES2018 all
  support this);
* a *`!!block` with the default blank-line end* (`\n\h*\n`);
* an *excluded region*, consumed and discarded as the *first* alternative so its interior never
  produces triple matches.

Illustrative combined pattern (sketch — not drop-in):

[source,regexp]
----
(?xms)
  # (1) excluded region: match first, ignore the capture → interior yields no triples
    ^.*? (?:ddot\.it/off|!!off) \b .*?  ^.*? (?:ddot\.it/on|!!on) \b .*?$
  # (2) a !!block filling the object, optional custom end marker via backreference
  | ^\h* (?<bsubj>[^\n]*?)\h*\.\.\h*(?<brel>[^\n]*?)\h*\.\.\h*
        (?:ddot\.it/|!!)block(?:\?end=(?<end>\S+))?\h*\n
        (?<body>.*?)
        (?:\n\h*\k<end>\h*$ | \n\h*\n)
  # (3) ordinary triple (typed/untyped) + optional inline or block metadata
  | ^\h* (?<subj>[^\n]*?)\h*
        (?: \.{4} | \.\.\h*\.\. | \.\.\h*(?<rel>[^\n]*?)\h*\.\. )
        \h* (?<obj>(?:(?!,,).)*?) \h*
        (?: ,,\h*(?<imeta>[^\n]*) | ,,\h*\n(?<mblock>.*?)\n\h*,, )? \h*$
----

WARNING: Sketches like this one gloss over the *run-length* rule (<<lexing>>). `\.{2}` happily
matches the first two dots of `...`, which ddot.it forbids. A real implementation needs the
lookaround forms `+(?<!\.)\.{2}(?!\.)+` and `+(?<!\.)\.{4}(?!\.)+` everywhere an operator is
matched. This is the single most common way to get a ddot.it lexer subtly wrong.

=== What one regex *cannot* do — and why

[cols="1,3",options="header"]
|===
| Blocker | Why a stateless regex can't

| *Subject inheritance*
| A continuation line (`..rel.. val`) leaves `subj` empty; the value belongs to a *previous*
  match. A regex can *capture* the empty group but cannot *substitute* the inherited subject into
  its output. That requires a `lastSubject` register carried in code — the "+registers" of the
  <<smallest-model,finite-state transducer with registers>> model.

| *Assembling block values*
| The regex can *delimit* a `!!block` body, but joining interior newlines as `\n`, stripping the
  end marker, and splicing the result into the interrupted field is post-processing on the
  capture, not matching. So is <<continuation,resuming the logical line>> afterwards.

| *Choosing the meta shape*
| Whether a `,,` payload is a list of `..type.. value` pairs or a single `text` pair is a
  decision about the *whole* payload, taken after scanning it. A regex can match either shape;
  picking between them and emitting the right relation is code.
|===

[[regex-capture-subject]]
=== "Why not just capture `..rel.. object` so nothing is remembered?"

Because a capture group can only capture *text that is present inside the match*, and on a
*continuation line the subject is not present* — it sits on an earlier line:

....
Dirk Hagemann ..works at.. SAP      <- subject is here
..knows.. Claudia Stern             <- this line has NO subject to capture
..phone.. 123                       <- nor this one
....

*So push that "somewhere" into the regex — by widening the match. This works, and it does remove
the cross-line register.* A continuation line is structurally recognisable ("a line beginning
with `..`"), so one match can cover the *subject line plus its whole run of continuation lines*,
capturing the subject once and repeating the pair group:

[source,regexp]
----
(?xm)
  ^\h*(?<subj>(?:(?!\.\.).)+?)\h*\.\.\h*(?<rel>.*?)\h*\.\.\h*(?<obj>.+?)\h*$   # subject line
  (?:\n\h*\.\.\h*(?<rel>.*?)\h*\.\.\h*(?<obj>.+?)\h*$ )*                       # continuations
----

Now the subject *is* inside the match: each match is self-contained, and no `lastSubject`
variable is carried between matches.

Two things still need care — one foldable into the pattern, one not:

. *Inheritance across a gap (foldable).* Blank lines do **not** break the chain
  (<<no-chunking>>), and a plain `(?:\n\h*\.\..*)*` repeat stops at the first line that is not a
  continuation. Fold the gap *into* the repeat so a single match spans it:
+
[source,regexp]
----
(?: \n\h*$                                                        # blank line, no capture
  | \n\h*\.\.\h*(?<rel>.*?)\h*\.\.\h*(?<obj>.+?)\h*$ )*
----
+
An `!!off` … `!!on` region is different: it *does* break the chain, because it ends a
<<snippets,snippet>>. There the repeat must *stop*.

. *Reading back the repeated captures (the one real wall).* In PCRE, JS, Java, Python, and Go a
  quantified group `(?<rel>…)*` retains *only its last iteration* — so although the match
  *covers* every pair, you cannot pull them all out of the groups. The exception is *.NET*, whose
  `Group.Captures` exposes every iteration. Everywhere else you *re-scan the matched block
  line-by-line* — a *local* loop over one match's own text, not cross-line state.

Bottom line: *widening the match does what you want*, and on *.NET* you get all pairs with no
remembered state at all. In the other engines the only residual is *local iteration* to extract
the repeated captures. At that point the choice between "one wide pattern + a per-match re-scan"
and "a line loop + a one-word `lastSubject`" is an engineering taste call, not a capability
limit — both are regular, neither needs a stack.

[[regex-dotnet]]
=== The .NET version (all captures — no remembered state)

[source,csharp]
----
using System.Text.RegularExpressions;

// .NET has no \h, so [ \t] is horizontal whitespace. IgnorePatternWhitespace
// lets us comment; whitespace inside [ ] stays literal. No Singleline ⇒ . ≠ \n.
var rx = new Regex(@"
    ^[ \t]*(?<subj>(?:(?!\.\.).)+?)[ \t]*\.\.[ \t]*(?<rel>.*?)[ \t]*\.\.[ \t]*(?<obj>.+?)[ \t]*$
    (?:                                                                       # then, repeatedly:
        \n[ \t]*$                                                             #  skip a blank line
      | \n[ \t]*\.\.[ \t]*(?<rel>.*?)[ \t]*\.\.[ \t]*(?<obj>.+?)[ \t]*$       #  or a continuation
    )*",
    RegexOptions.Multiline | RegexOptions.IgnorePatternWhitespace);

foreach (Match m in rx.Matches(text))
{
    string subject = m.Groups["subj"].Value.Trim();
    CaptureCollection rels = m.Groups["rel"].Captures;   // ALL iterations, in source order
    CaptureCollection objs = m.Groups["obj"].Captures;
    for (int k = 0; k < rels.Count; k++)                 // rel[k] is paired with obj[k]
        Emit(subject, rels[k].Value.Trim(), objs[k].Value.Trim());
}
// (inline ',,' metadata, ....-untyped links, and !!block expansion elided for focus)
----

The `(?<rel>…)` / `(?<obj>…)` names appear in *both* the subject-line part and the continuation
part; .NET accumulates every hit into one ordered `CaptureCollection`. Because each triple
contributes exactly one `rel` and one `obj` together — and the blank-line branch contributes
neither — the two collections stay index-aligned. There is no `lastSubject` variable at all.

[[regex-typescript]]
=== The TypeScript version (re-scan — JS keeps only the last capture)

*JS/TS has no `Group.Captures` equivalent.* A quantified group yields only its *last* value;
`matchAll` iterates *matches*, not captures within one match; and you *cannot even declare*
`(?<rel>…)` twice in sequence — duplicate named groups are legal only across mutually-exclusive
alternatives (since ES2025). So the all-captures trick is unavailable, and the idiomatic form is
the line loop with a one-word register:

[source,typescript]
----
let currentSubject: string | null = null;
for (let i = 0; i < lines.length; i++) {
  // …handle !!off/!!on, an open ',,' block, and !!block bodies first (elided)…
  const t = readTriple(lines[i].trim(), currentSubject);   // empty subject ⇒ inherit
  if (!t) continue;                                        // NotATriple ⇒ emit nothing
  currentSubject = t.from;                                 // the register
  events.push({ from: t.from, type: t.type, to: t.to, kind, source, location: i + 1 });
}
----

This is the shape the reference implementation ships
(link:../../ddot.it-syntax-tools/parser/[`@calpano/ddot-parser`]).

.Could the TS parser use *just one* regex?
[NOTE]
====
* *One regex + a one-word variable:* *yes* — the loop above is essentially this.
* *One regex, zero state:* *not in practice.* Two engine facts block it: a quantified group keeps
  only its *last* capture, and a continuation line does not contain its subject. The only
  stateless escape is a *variable-length lookbehind* (V8 supports it) re-deriving the subject for
  each continuation — fragile, O(n²)-ish, and it still cannot handle `!!block` splicing. Not
  worth it.
====

=== Practical answer

* *Match a single triple + its metadata (and even a single `!!block` with a backreferenced
  `?end=`) in one regex:* *yes.*
* *Parse a whole document into correct events with one regex alone:* *no* — you need a *thin code
  loop* around the global regex to carry the subject register, splice block bodies, and assemble
  meta.

That is exactly the model from <<smallest-model>>: regex expresses the *regular* structure; the
*transduction* needs the register layer.

[[algorithm]]
== Reference algorithm (pseudo-code)

Since a loop is unavoidable, the *most comprehensible* parser is the line-oriented state machine
below — one pass over the lines, a handful of named state variables, and small pure helpers.

=== Main loop

[source,text]
----
function parse(text, kind, source) -> list<Event>:
    text  = normalizeNewlines(text)     # CR LF → LF, CR → LF   (see “Newline normalisation”)
    lines = split(text, "\n")           # keep empty lines; i is 0-based

    events   = []
    subject  = null     # last subject — filled into continuation lines (inheritance)
    openMeta = null     # the event whose ',,' block is currently open (or null)
    excluded = false    # inside a !!off … !!on region?

    i = 0
    while i < length(lines):
        raw  = lines[i]
        line = trim(raw)

        # (1) pre-parse commands — recognised ANYWHERE on the line, not just alone on it.
        #     The carrying line is a directive line: it yields no triple.
        if containsCommand(raw, "off"):
            excluded = true;  openMeta = null;  subject = null;  i += 1;  continue
        if containsCommand(raw, "on"):
            excluded = false; openMeta = null;  subject = null;  i += 1;  continue
        if excluded:
            i += 1;  continue                      # excluded region → emit nothing

        # (2) blank line: no triple, and NO reset — the subject survives it
        if line == "":
            i += 1;  continue

        # (3) inside an open multi-line ',,' metadata block
        if openMeta != null:
            if line == ",,":                       # closing delimiter
                openMeta = null
            else:
                addMetaLine(openMeta, line)        # one meta line → a pair, or text
            i += 1;  continue

        # (4) a line-initial ',,' opens a block for the PREVIOUS triple (one-token lookahead)
        if line == ",,":
            openMeta = last(events);  i += 1;  continue

        # (5) an ordinary line: try to read a triple
        (t, i) = readTriple(lines, i, subject)     # consumes !!block bodies + continuations
        if t == null:
            i += 1;  continue                      # NotATriple → emit nothing, no error
        subject = t.from                           # inherited by later lines
        event   = Event(from=t.from, type=t.type, to=t.to, kind, source, location=t.line)

        if t.metaText == "":                       # bare trailing ',,' → open a block
            openMeta = event
        else if t.metaText != null:                # inline ',, …' → pairs or text
            addMeta(event, t.metaText)

        append(events, event)

    return events
----

Four things in that loop are easy to get wrong, and each is pinned by a corpus case:

`!!off` is a *substring* test, not a line comparison::
It must fire inside a host comment (`31-off-in-comment`). The *name* is still matched exactly, so
`!!office` is not `!!off`.

A blank line resets *nothing*::
See <<no-chunking>>. The subject survives blank lines to the end of the file.

A line-initial `,,` needs one token of lookahead::
`,,` alone on a line opens a block for the previous triple (`09-standalone-comma-block`); `,,`
followed by more text on the same line is the *start of a subject*.

`readTriple` may consume many lines::
A `!!block` opener swallows its body and the logical line may then *continue*
(`29-block-subject`, `32-chained-blocks`, `33-meta-block-continuation`). That is why it returns
the new index.

=== Helpers

[source,text]
----
# Split a line into subject / relation / object (+ trailing metadata). Only the operators
# that DELIMIT slots are operators; everything after the last one is the object, verbatim.
function readTripleLine(line, inheritedSubject) -> Triple | null:
    (body, metaText) = splitOnce(line, CM2)      # metaText = text after the first ',,', or null

    op1 = nextOperator(body, from=0)             # a DT4 run, or a DT2 run — see nextOperator
    if op1 == null: return null                  # no operator at all → not a triple

    if op1.dots == 4:                            #  SUBJECT .... OBJECT   (untyped)
        subj = trim(body[0 .. op1.start]);  type = null;  obj = trim(body[op1.end ..])
    else:                                        #  SUBJECT .. RELATION .. OBJECT
        op2 = nextOperator(body, from=op1.end)
        if op2 == null: return null              # only one '..' → not a triple
        subj = trim(body[0 .. op1.start])
        type = trim(body[op1.end .. op2.start])
        obj  = trim(body[op2.end ..])            # REST of line, verbatim → '../../foo.txt' intact
        if type == "": type = null               # '.. ..' (empty relation) == untyped

    if obj == "": return null                    # empty object → not a triple
    from = (subj != "") ? subj : inheritedSubject
    if from == null: return null                 # nothing to inherit → not a triple
    return Triple(from, type, obj, metaText)

# THE run-length rule. A maximal run of dots is an operator only at length 2 or 4.
function nextOperator(s, from) -> {start, end, dots} | null:
    scan s from 'from' for a maximal run of '.'
    if run length == 2 or run length == 4: return it
    otherwise skip it and keep scanning        # 1, 3, 5, … dots are ordinary text

# A ',,' payload → meta pairs on the event.
function addMeta(event, metaText):
    pairs = readMetaPairs(metaText)            # split on SC2, then '..rel.. value' each
    if pairs is non-empty:
        for (type, value) in pairs: append(event.meta, {type, to: value})
    else:
        append(event.meta, {type: "text", to: trim(metaText)})   # free text → built-in 'text'

# Inline pairs are separated by ';;' — REQUIRED, because a value may contain '..'.
function readMetaPairs(s) -> list<(type, value)>:
    pairs = []
    for segment in splitOn(s, SC2):
        a = nextOperator(segment, 0);      if a == null: return []   # not the pair shape
        if a.dots == 4:
            append(pairs, (null, trim(segment[a.end ..])))           # untyped ⇒ 'links to'
        else:
            b = nextOperator(segment, a.end);  if b == null: return []
            append(pairs, (trim(segment[a.end .. b.start]), trim(segment[b.end ..])))
    return pairs

# A !!block body: capture following lines up to the terminator.
function readBlock(lines, start, command) -> (value, nextIndex):
    marker = endParam(command)             # '?end=X' → "X";  else null ⇒ terminator is a blank line
    body = [];  i = start
    while i < length(lines):
        if marker == null and trim(lines[i]) == "":     break            # blank line, NOT consumed
        if marker != null and trim(lines[i]) == marker: i += 1;  break   # marker line, consumed
        append(body, lines[i]);  i += 1
    return (join(body, "\n"), i)           # interior newlines become '\n' in the value
----

[[pipeline]]
== Where a parser sits in the pipeline

ddot.it separates *reading* from *collecting*
(link:../site/spec/ddot-it-parse.adoc#two-layers[Parse Spec → Two layers]):

. A *reader* (the parser you are writing) knows how to pull ddot.it text out of one *host
  language* (Markdown, YAML, Java, HTML, plain text, …) and emits *triple events*.
. A *collector* combines all events into one knowledge graph and does the resolution a single
  reader cannot — substituting `source` for `ddot.it/this`, defaulting an absent `type` to
  `links to`, applying `prefix`, merging duplicates.

[IMPORTANT]
====
Your parser's job ends at *emitting triple events*. It resolves *no* in-text command: `!!this`
and any `ddot.it/<name>` pass through as literal slot text, whatever the name. Only the three
<<preparse,pre-parse commands>> — `!!off`, `!!on`, `!!block` — are acted on, and they are handled
*before* the grammar runs, so they never appear in your output either.
====

[[levels]]
=== Three levels of conformance

Separately-tested contracts. An implementation only needs the one relevant to its concern
(link:../test-data/README.md[test-data/README.md]):

[cols="1,3,2",options="header"]
|===
| Level | Produces | Golden file

| *Event parser*
| JSONL triple events
| `expected.events.jsonl`

| *Highlighter / lexer*
| A flat token stream `{line,start,end,token,text}`
| `expected.tokens.json`

| *Preview renderer*
| Role-classed HTML spans
| `expected.body.html`
|===

The lexer and the event parser *agree*. The one place they used to differ — plain-text metadata,
which the lexer tokenised as `meta-text` while the event parser dropped it — was settled in 1.3
in the lexer's favour: free meta text is real metadata carrying the built-in
link:../site/spec/ddot-it-vocabulary.adoc#text[`text`] relation. Cases `09`, `13`, `14` and `27`
pin both streams.

[[preprocessing]]
== Input preprocessing

[[newlines]]
=== Newline normalisation

Apply *before* parsing:

. `CR LF` → `NL`
. `LF` → `NL`
. `CR` → `NL`

The order matters: CRLF must be tested first, or the `CR` of a CRLF matches and leaves the `LF`
behind as a second newline. After normalisation the only line terminator is `\n`. Split with a
limit that *preserves trailing empty lines* (`text.split("\n", -1)` in Java, plain
`split("\n")` in JS) so line numbering stays correct.

The end of input acts as an *implicit newline*: a final line without a trailing break is an
ordinary line, and a triple on it is emitted normally.

[[lexing]]
=== The token alphabet

Only five two-or-four character runs have a special role. Everything else is text.

[cols="1l,3,3l",options="header"]
|===
| Token | Meaning | Regex
| DT2 | exactly two dots              | (?<!\.)\.{2}(?!\.)
| DT4 | exactly four dots             | (?<!\.)\.{4}(?!\.)
| CM2 | exactly two commas            | (?<!,),{2}(?!,)
| SC2 | exactly two semicolons        | (?<!;);{2}(?!;)
| EM2 | exactly two exclamation marks | (?<!!)!{2}(?!!)
|===

[IMPORTANT]
====
*Symbol characters are grouped into maximal runs, and a run is a special token only at its exact
length.* A single `.`, a run of three or five dots, a lone `,` or `;` or `!` — all ordinary text.
This is what makes `Node.js`, `Mr. Smith`, `U.S.A.` and an ellipsis safe: none of them contains
an operator, so none can become a triple by accident (case `12-dotted-subject`).

The lookarounds are not decoration. `\.{2}` alone matches the first two dots of `...`, which is
exactly what the rule forbids.
====

[[whitespace]]
=== Whitespace

`WS` is **TAB plus every Unicode space separator** (category `Zs`) — never a newline. It is
stripped from the start and end of every slot, inline and block alike:

  Dirk Hagemann   .. works at ..  Big Corp   →   (Dirk Hagemann, works at, Big Corp)

Internal whitespace is preserved (`Project Eagle` stays two words).

[[model]]
== The document model

[[no-chunking]]
=== There is no chunking construct

A document is *a sequence of lines*. An omitted subject continues the subject of the previous
line — across blank lines, to the end of the file.

[source,ddot.it]
----
Alice ..knows.. Bob

..likes.. Tea
----

states `Alice ..likes.. Tea`.

WARNING: This *changed in 1.3*. Earlier versions chunked text at three consecutive newlines and
reset the subject and meta-mode at each boundary. If you are porting an older implementation,
delete the blank-line counter — do not carry it forward.

[[snippets]]
=== Snippets: the one thing that does reset

`!!off` … `!!on` splits a chunk into *snippets*. Subject inheritance works *within* a snippet,
not across snippet boundaries, so an `!!off`/`!!on` pair does break the chain. Every snippet of a
chunk shares that chunk's source URI, and line numbers stay relative to the chunk.

[[preparse]]
=== Pre-parse commands

Three commands are handled *before* the grammar runs, and none appears in the output:

`!!off` / `!!on`::
Recognised **anywhere on a line** — not only alone on one. This is what lets them ride inside a
host comment (`+<!-- ddot.it/off -->+`, `+// !!on+`), which is how they are almost always
written. The carrying line is a *directive line*: it yields no triple, and the region begins with
the **following** line. Cases `06-off-on-toggle`, `31-off-in-comment`.
+
CAUTION: Because recognition is position-independent, prose *about* the command triggers it. A
document discussing ddot.it must keep such mentions inside a `!!block`, where commands are inert.

`!!block`::
Recognised **only when it fills a whole position** and **ends its physical line** — see
<<blocks>>. A `!!block` inside running text is inert.

[[blocks]]
=== `!!block`: multi-line and verbatim values

`!!block` opens a verbatim region when it is the *entire content* of one of four positions:
`Subject`, `Object`, `MetaObject`, or the free meta text after `,,`. (Not `Relation` or
`MetaRelation` — those hold names, where a multi-line value has no use.) The opener must have
end-of-line to its right; nothing may follow it on that line.

* The **body** runs from the next line to the terminator: the first *blank line*, or the line
  equal to the `?end=MARKER` marker. The marker line is not part of the value, and with a marker
  present blank lines no longer terminate. If the terminator never arrives, the block runs to the
  end of the chunk.
* Interior newlines become real `\n` in the value.
* Nothing in the body is interpreted — `..`, `,,` and commands are all literal.

[[continuation]]
.Continuation
The spliced-in field is *sealed*, and the logical line then *resumes* if the line after the
terminator starts with the token the interrupted position accepts:

[cols="1,3",options="header"]
|===
| Interrupted position | Continues on
| Subject     | `DT2` or `DT4` — `+..knows.. Bob+`
| Object      | `CM2` — `+,, ..since.. 2016+`
| MetaObject  | `SC2` — `+;; ..until.. 2020+`
| meta text   | nothing — the logical line always ends
|===

Anything else starts a fresh line. So one logical line can carry several blocks
(`32-chained-blocks`):

[source,ddot.it]
----
!!block
Alice
Anderson

..knows.. !!block
Bob
Baker

,, ..since.. 2016
----

reads as `Alice⏎Anderson ..knows.. Bob⏎Baker` with one meta pair.

NOTE: Two openers on *one* physical line is impossible by construction: an opener must have
end-of-line to its right. In `+!!block ..knows.. !!block+` the first token has `DT2` to its right
and is therefore inert — the subject is the literal string `!!block`. Only the second opens.

Cases: `17-block` (blank-line form), `21-block-end-marker` (marked form), `29-block-subject`,
`30-block-meta-object`, `32-chained-blocks`, `33-meta-block-continuation`.

[[triples]]
== Triples

=== Typed and untyped links

....
aaa ..bbb.. ccc          typed:   relation "bbb"
aaa .... ccc             untyped
aaa .. .. ccc            untyped — the same operator, spelled with a space
....

An untyped link has *no relation*, and the event **omits** `type` entirely rather than writing
`links to` into it; a consumer defaults a missing `type` to
link:../site/spec/ddot-it-vocabulary.adoc#links-to[`links to`]. Cases `01-simple-triple`,
`02-untyped-link`, `10-spaced-untyped`.

NOTE: The highlighter emits the whole literal `.. ..` — inner whitespace included — as *one*
`doubledot` token (`10-spaced-untyped`). Parser and lexer agree that it is one operator.

[[object-literal]]
=== Objects may contain `..`

A `..` / `....` is an operator *only where it delimits a slot*. Once the slots are established —
one operator for untyped, two for typed — *everything remaining on the line is the object, taken
verbatim*:

....
a ..path.. ../../foo.txt      → (a, path, ../../foo.txt)
a ..spec.. http://h/x..y      → (a, spec, http://h/x..y)
....

Case `20-object-dotdot` pins both.

[IMPORTANT]
====
Practically: do *not* "split on all separators and require three segments". Instead find operator
1; if it is `DT2`, find operator 2; then take the rest of the line. The *space* separating the
relation's closing `..` from an object that itself starts with `..` is what marks the boundary —
without it the dots run together into a longer run, which is not an operator at all.

Subject and relation get no such freedom: `Subject := TextExcept{NL,DT2,DT4}`. A subject
containing `..` can only be written with `!!block` (`29-block-subject`).
====

=== What is *not* a triple

A line yields **no event** — and no error — when:

* it contains no operator, or only one `DT2`;
* the object is empty (`a ..b..` with nothing after);
* the subject is omitted and there is nothing to inherit;
* an enclosing multi-line construct (a `,,` block) never closes — then *every* line it spans
  yields nothing.

Case `23-not-a-triple` has an empty `expected.events.jsonl`, which is the whole point: a
non-triple is invisible, not an error. Ordinary prose is safe.

[[inheritance]]
== Subject inheritance

Omit the subject to attach more properties to the *previous* subject:

....
Dirk Hagemann ..works at.. SAP
..knows.. Claudia Stern
..phone.. 123-456-789
....

Mechanism: set the register on every emitted triple; a line beginning with a leading `..` yields
an empty first slot, which falls back to the register. Case
`07-leading-separator-continuation`, and `26-untyped-continuation` for the `....` form.

[CAUTION]
====
For the *highlighter*, do *not* pre-seed the slot index to 1 on continuation lines. The leading
`..` operator naturally advances the slot counter, so the next segment is classed as the
relation. Pre-setting double-counts and mis-classes it as an object.
====

[[metadata]]
== Metadata (`,,`)

Metadata attaches to *the whole triple* on whose line — or whose following block — it appears.
Not to the object: `John ..leads.. Eagle ,, ..since.. 2025` says the *leading* is since 2025.

The `,,` is found by its *first occurrence* on the line; everything before is the triple body,
everything after is the meta payload.

=== Inline metadata, and the `;;` separator

....
John Doe ..leads.. Project Eagle ,, ..since.. 2025 ;; ..until.. 2027
....

yields two pairs (`22-inline-meta-separator`). *The separator is required.* A meta value runs to
the end of the line or to the next `;;`, and may itself contain `..`, so

....
,, ..since.. 2010 ..until.. 2020
....

is *one* pair whose value is the literal text `2010 ..until.. 2020`. Inside a multi-line `,,`
block there is no separator at all — each value runs to the end of its own line, so a `;;` there
is ordinary text (`28-semicolon-in-meta-block`).

[[meta-block]]
=== The multi-line block

A *bare trailing* `,,` opens a block; a *bare* `,,` on its own line closes it:

....
Dirk Hagemann ..works at.. SAP ,,
..year.. 2010
..fictive.. yes
,,
....

The opening `,,` may instead stand alone on the line *immediately* after the triple — both
spellings attach to the same triple (`04-multiline-meta`, `09-standalone-comma-block`). A blank
line in between breaks the attachment. The block may be empty (`25-empty-meta-block`), and an
unclosed block yields *nothing at all* for every line it spans.

This is the one place needing a token of lookahead: a line-initial `,,` opens a block only if a
newline follows it; otherwise it is the start of a subject that happens to begin with `,,`.

=== Pairs or text, never both

A meta part holds *either* `..relation.. value` pairs *or* free text.

[cols="3,4",options="header"]
|===
| Syntax | Meta pair emitted
| `+,, ..since.. 2016+`      | `+{"type":"since","to":"2016"}+`
| `+,, .... 2025+`           | `+{"to":"2025"}+` — untyped, so `links to`
| `+,, a random note+`       | `+{"type":"text","to":"a random note"}+`
|===

*Free text carries the built-in `text` relation, not `links to`.* These are the only two built-in
relations in the language. Cases `03`, `24`, `13`, `14`, `27`, `09`.

[[commands]]
== Commands

A command has four interchangeable spellings, and the *slash and a non-empty name are required*:

[source,ebnf]
----
command-begin := 'https://ddot.it/' | 'http://ddot.it/' | 'ddot.it/' | '!!'
command       := command-begin command-name uri-query? uri-fragment?
command-name  := one or more characters that are not WS, NL, '?' or '#'
uri-query     := '?' then any characters up to WS, NL or '#'
uri-fragment  := '#' then any characters up to WS or NL
----

A command ends at the first `WS` (see <<whitespace>>) or newline — and at nothing else. `?` and `#`
do **not** terminate it; they introduce its query and fragment, which are *part of* it. So
`+!!block?end=END+` is one command with name `block` and query `?end=END`.

Bare `ddot.it` — no slash, no name — is **not** a command. It is a document *marker*: prose may
mention the project, and a URL may point at the site, without either becoming a command.

[[registry-free]]
=== Command syntax is registry-free

*Recognition never consults a list of known names.* Anything matching a command spelling is a
command token, whether or not the name is one any specification defines. Two consequences:

* A parser or highlighter needs *no list of commands* and stays correct as they are added or
  retired. `!!label` is still lexed and highlighted as a command even though `label` is no longer
  one — case `15-label`.
* Deciding what a command *means* — including that an unknown or retired one means nothing —
  belongs to the interpreting layer, never to the parser.

This is also what makes a ddot.it *URI value* work without new syntax. An object like
`+https://ddot.it/vocabulary/2026-07-20#entity+` is command-shaped; the parser tags it, the
interpreting layer finds no such command, and the field keeps its plain value — which is exactly
what `..uri..` wants. Keep command names short and at the root, and keep URI values on deeper
paths, so the two spaces do not collide.

=== What a parser actually acts on

[cols="2,3,2",options="header"]
|===
| Command | Handling | Evidence
| `!!off` / `!!on`
| Pre-parse. Toggle the excluded region; never emitted.
| `06`, `11`, `31`

| `!!block`
| Pre-parse. Its body becomes the value of the position it fills; never emitted.
| `17`, `21`, `29`, `30`, `32`, `33`

| `!!this`
| *Literal slot text* — `from: "ddot.it/this"` or `from: "!!this"`, whichever was written. The
  collector substitutes the source URI.
| `05`, `11`, `16`

| anything else
| *Literal slot text.* No exceptions.
| `15-label` (`type: "!!label"`)
|===

NOTE: `ddot.it/verbatim` was *planned and then dropped* in 1.3: `!!block` already takes its body
verbatim, so a second escaping command said nothing new. If you are porting an implementation
that has a `verbatim` mode, delete it.

[[events]]
== Output: triple events

Emit one JSON object per recognised triple, as JSONL. **The normative definition is
link:../site/spec/ddot-it-parse.adoc#events[Parse Spec → Triple Events]**; the table below is the
working summary.

[cols="1l,1,4",options="header"]
|===
| Field | Req. | Meaning
| from     | yes | Subject; already substituted if the line omitted it
| type     | no  | Relation. *Omit* for untyped links — do not write `links to`
| to       | yes | Object; never empty
| meta     | no  | Array of `{type?, to}`, in source order. Omit when empty — never `[]`
| kind     | yes | Host format (`ddot`, `markdown`, …); fixed per reader
| source   | yes | The chunk's source URI
| location | yes | *1-based* line number of the triple's first line
|===

Example (`03-inline-meta`):

[source,json]
----
{"from":"John Doe","type":"leads","to":"Project Eagle","meta":[{"type":"since","to":"2025"}],"kind":"ddot","source":"input.ddot","location":1}
----

=== Serialisation contract

The golden JSONL is *byte-exact*:

* **Key order** on an event: `from`, `type`, `to`, `meta`, `kind`, `source`, `location`, absent
  optionals simply left out. Within a meta pair: `type`, `to`.
* **Escaping** covers `\"`, `\\`, `\n`, `\r`, `\t`, `\b`, `\f`, and `\uXXXX` for other control
  characters. Nothing else — `/`, `<`, `>` and `&` are written as-is.
* **No insignificant whitespace**: no space after `:` or `,`, no indentation.
* One event per line, `\n`-separated, UTF-8, no enclosing array.

=== Values are verbatim

Slot values are taken as-is. Quotes are ordinary characters belonging to the slot, so
`"a sample document"` keeps them (`05-command`). Angle brackets and ampersands are *not*
HTML-escaped: `+<https://example.com/x?a=1&b=2>+` is emitted intact (`08-html-escaping`).
HTML-escaping applies only to the *preview renderer's* output, never to events or tokens.

A field filled by a `!!block` carries the body's real newlines, which become `\n` in the JSON
string (`17-block`, `29-block-subject`).

[[highlighter]]
== The highlighter / token contract

If you are building a syntax highlighter rather than an event parser, target
`expected.tokens.json`: a flat array of `{line, start, end, token, text}`, *zero-indexed*,
*end-exclusive*, *whitespace not tokenised*, lines with no tokens omitted.

Token vocabulary (link:../test-data/tokens.md[tokens.md] is normative):

[cols="1l,3",options="header"]
|===
| Token | Covers
| subject        | first slot of a triple
| relation       | relation slot of a typed triple
| object         | object slot
| doubledot      | `..` / `....` / `.. ..` (the last is one token)
| command        | `ddot.it`, `ddot.it/<name>`, `!!`, `!!<name>`
| command-param  | a command's query or fragment (`?end=`, `#frag`)
| meta-delim     | `,,` opening or closing metadata
| meta-separator | `;;` between inline pairs
| meta-doubledot | `..` / `....` inside metadata
| meta-relation  | relation inside metadata
| meta-object    | object inside metadata
| meta-text      | free-form text in a `,,` context
| excluded       | body of an `off`…`on` span (markers stay `command`)
| verbatim       | body of a `!!block` span (opener stays `command`)
| block-end      | the `?end=` marker — *both* occurrences
|===

WARNING: These names changed in 1.3: `operator` → `doubledot`, `meta-operator` →
`meta-doubledot`, `disabled` → `excluded`, plus the new `meta-separator`, `command-param`,
`block-end` and `verbatim`. Highlighters and themes keyed on the old names need updating.

Key rules:

* Quoted strings are *not* a token type — quotes belong to their slot.
* When a slot's text is *exactly* a command form, emit `command`, not the slot role (`05`, `15`).
* `!!block?end=MARKER` is *three* tokens — `command`, `command-param`, `block-end` — and the
  terminator line is a fourth `block-end`, so opener and terminator can be styled as a pair.
* An unterminated construct may be coloured to the end of the document even though the *parse*
  emits nothing for it. A line-at-a-time highlighter cannot revisit lines it has already
  coloured, and this divergence is confined to presentation of already-malformed input.

The canonical generator is the TextMate grammar
link:../../ddot.it-syntax-tools/textmate/ddot.tmLanguage.json[`ddot.tmLanguage.json`] (npm
`@calpano/ddot-textmate-grammar`); Pygments, Chroma, highlight.js, Prism, Rouge and Shiki
implementations map their native scopes onto the same vocabulary.

[[relations]]
== Relation names are not a parser concern

Relations are *just strings* to a parser. `has type`, `same as`, `links to`, `prefix` and the
rest are conventions resolved by consumers — see the
link:../site/spec/ddot-it-vocabulary.adoc[Vocabulary Specification] and case
`18-relation-aliases`.

Exactly *two* relations are built into parsing, and only because they are what a syntax shortcut
expands to:

* link:../site/spec/ddot-it-vocabulary.adoc#links-to[`links to`] — the untyped `....` link;
  emitted as an *absent* `type`.
* link:../site/spec/ddot-it-vocabulary.adoc#text[`text`] — free metadata text; emitted as
  `type: "text"`.

The `prefix` relation supports optional RDF interpretation (a name `A:foo` may have `A:` replaced
by the mapped IRI). That is a *downstream* interpretation, not required of a parser — case
`19-rdf-prefix` emits `prefix` as an ordinary triple.

[[host-languages]]
== Host-language extraction (reader front-ends)

Your parser core consumes plain ddot.it text. A *reader* first extracts that text from a host
document:

[cols="1,3",options="header"]
|===
| Host | Where ddot.it text is found
| link:../site/reader-markdown.md[Markdown]
| plain text, `<!-- -->` comments, fenced code blocks, section attributes `{#id .class}`
| link:../site/reader-asciidoc.md[AsciiDoc]
| plain text, `//` and `////` comments, `----` listing blocks, block attributes `[#id.class]`
| link:../site/reader-html.md[HTML]
| `<!-- -->` comments, element text, `data-ddot` attributes, `<ddot-it>` custom element
| link:../site/reader-xml.md[XML / pom.xml]
| comments, element text (esp. `<description>`)
| link:../site/reader-yaml.md[YAML]
| `#` comments, scalar string values (each value resets parse context)
| link:../site/reader-java.md[Java]
| line/block/Javadoc comments, `@DdotIt(String[])` annotation values (newline-joined)
| link:../site/reader-plaintext.md[Plain text]
| any line
| link:../site/reader-powerpoint.md[PowerPoint]
| slide text + speaker notes (`.pptx` = zipped XML)
|===

Three extraction rules worth flagging:

* *Section/block attributes* expand to synthetic triples: `## Title {#a .b}` becomes
  `Title ..has tag.. a` + `..has type.. b`.
* `<ddot-it>` elements can carry a multi-line `text` value with real newlines — the only place
  besides `!!block` where a value contains `\n`.
* YAML resets parse context per scalar string, so subject inheritance does not cross value
  boundaries.

[CAUTION]
====
A *host-aware* reader that strips comments before handing text over will also strip any
`!!off`/`!!on` inside them, losing that steering. A host-aware parser SHOULD *preserve*
pre-parse commands found in host comments rather than discarding them — the Vocabulary
Specification steers its own indexing exactly this way.
====

[[open]]
== Known divergences

Both of the questions that were open here in 1.2 are now settled, and each turned out to be a
*real disagreement between implementations* rather than a gap in the prose. They are recorded
because a port of an older implementation will still have the old behaviour:

Unicode whitespace::
`WS` is TAB plus the whole `Zs` category (<<whitespace>>). Before this was decided, the event
parser accepted NBSP (a side effect of JavaScript's `trim`) while the TextMate grammar did not
(`[ \t]` throughout), so `+a<NBSP>..rel..<NBSP>b+` produced the subject `a` in one and
`+a<NBSP>+` in the other -- two different graph nodes, from input that looks identical on
screen. Both now widen to `Zs`. Corpus case `35-unicode-whitespace` pins it, including that
U+200B ZERO WIDTH SPACE is *not* whitespace.

`!!block` in the meta-text position::
The specification allows it as a redundant alternative to the `,,` … `,,` block form. The event
parser and the preview renderer implemented it; the TextMate grammar had `block-subject`,
`block-verbatim` (object) and `block-metaobject` rules but no `block-metatext` pair, so the body
was left unhighlighted. The grammar now has it, and corpus case `34-block-meta-text` pins the
position that was previously untested.

Still outstanding, and deliberately not pinned by a corpus case:

* *The reference parser over-strips U+FEFF.* `@calpano/ddot-parser` trims with JavaScript's
  `trim()` / `\s`, which remove U+FEFF as well as `Zs`. Per <<whitespace>> and
  link:../site/spec/ddot-it-parse.adoc#chunk-preprocessing[chunk preprocessing], a U+FEFF is
  stripped only as a *leading BOM*; anywhere else it is ordinary text and belongs to its field.
  The divergence is confined to a mid-line U+FEFF, which is vanishingly rare, and fixing it means
  changing a published package — so it is documented rather than pinned. If you are writing a new
  parser, use an explicit `WS` class instead of your language's built-in trim; the reasons are in
  <<whitespace>>.

[[testing]]
== Conforming: how to test

Run your implementation against link:../test-data/cases/[`test-data/cases/`]. Each case provides
`input.ddot` plus the `expected.*` file for each level. Assert *byte-identical* output for your
level.

The reference implementation is `@calpano/ddot-parser`
(link:../../ddot.it-syntax-tools/parser/[`ddot.it-syntax-tools/parser/`]), which is what the
ddot.it vocabulary gate runs:

[source,sh]
----
(cd ../ddot.it-syntax-tools && npm run conformance:parser)   # tokens + events
(cd ../ddot.it-syntax-tools && npm run conformance)          # every highlighter
----

Regeneration commands and the CI `--check` flags are in
link:../test-data/README.md[test-data/README.md]. Note that `expected.events.jsonl` has *no*
regeneration step by design: it is written and reviewed deliberately, so that a behaviour change
is a decision rather than a diff.
