== Introduction
This document defines some basic relations and types, to be used in {dd}.
{ddd} itself is relation agnostic and can be used with any relations, including those defined in RDF.

There are only two built-in relations, representing syntax shortcuts from the parsing layer: <<text>> (for text annotating a triple, after the `,,` marker) and <<links-to>> (the default relation for the untyped link shortcut `+++....+++`).

[[monotonicity]]
=== Monotonicity
{ddd} is a *monotonic* modelling language, and the relations defined here preserve that.

Monotonic means: **adding a statement can never invalidate a conclusion already drawn.**
Whatever a reasoner infers from a set of triples it still infers after more triples arrive; inference
only ever adds, it never retracts. The formal statement is that if a knowledge base entails some
fact, then every superset of that knowledge base entails it too.

This follows from the language being _positive_: there is no way to write a negation, so no
statement can contradict another. **A monotonic language cannot produce contradictions** — the worst
that can happen is that it infers something you consider wrong, which is a modelling error, not a
logical one.

The practical payoff: triples from different files, authors and tools can simply be merged. No
statement can invalidate another, so there is no ordering, no precedence and no conflict resolution
to define. Every relation in this document is designed to keep that guarantee — see for instance how
<<has-subtype,cycles in `has subtype`>> collapse into <<same-as,`same as`>> instead of being an error.

RDFS, OWL and CDS are monotonic in the same way. Languages with negation, defaults or a closed-world
assumption are not: there, a later statement can withdraw an earlier conclusion.

=== Declaration Conventions
Every built-in in this document is declared with the same shape, so that a tool can load the
vocabulary without special-casing:

. **Canonical names are spelled out.** A built-in block always uses the canonical relation name
  (`has alias`, not `alias`; `same as`, not `is same as`). Alternative spellings appear only as
  `..has alias..` values.
. **Both sides of a pair are declared.** A relation and its <<has-inverse,inverse>> each get their
  own block with their own `has type`, `has supertype`, `has inverse` and `uri`.
. **Hierarchies point upwards only.** A built-in block states `has supertype`, never `has subtype`;
  each entry names its parent, so the full tree is the union of those edges. Only the three roots
  — <<type-entity,`entity`>> for types, <<related,`related`>> and <<property,`property`>> for
  relations — state no `has supertype` at all.
. **Symmetric relations are their own inverse.** For a relation of type <<symmetric-relation,`symmetric relation`>>
  the `has inverse` triple is implied and therefore not stated.
. **Every built-in has a `uri`** in the {dd} namespace (see <<prefix>>).
. **Only built-ins are machine-readable.** The document turns {dd} parsing off in its second line
  with an https://ddot.it/off[`https://ddot.it/off`] command, and each built-in block switches it
  back on with https://ddot.it/on[`https://ddot.it/on`] and off again straight after. Everything
  else — prose, `link:` macros, the `Given / Inferred` rules, the `Example` blocks and the CDS
  migration table — is therefore *never* parsed. Indexing this file with a {dd} tool yields exactly
  the built-in triples and nothing else:
+
[source,shell]
----
ddot index -f vocabulary.ddot --ext adoc site/spec/
----
+
The commands are written inside AsciiDoc comments (`+// https://ddot.it/off+`), so they steer the
parser without showing up in the rendered document.

=== Types `thing` and `value`
.Motivation
{ddd} has only one datatype: string.
So it cannot distinguish between, let's say `42` being the age of someone or it being the identifier for a chemical compound.  Everything is just an <<type-entity>>.

[[type-thing]]
.Type `thing`
We define `thing` to be all entities that are object-like, physical or imaginary concepts that can be named.
In RDF, these are _URIs_ or _Blank Nodes_.

== Usage in Formal Systems and Inference
For formal systems, such as rule and inference engines, a crucial question is: Are these two entities the same or different logical entities?
To make using {dd} easier, many relations define **aliases** that are alternative names denoting the same concept.


[[has-inverse]]
=== Relation `has inverse`
.Motivation
Often relations form natural pairs, depending on their direction.
A _Person_ _works for_ a _Company_. In the other direction,
a _Company_ _employs_ a _Person_. So `works for` and `employs` express the same fact, but stated from a different perspective.
For many use cases, the distinction should be ignored.
Like in OWL, {dd} allows to explicitly state the inverse relation of a relation.

.Given / Inferred
[ddot.it]
----
a ..ppp.. b
ppp ..has inverse.. qqq
_____________________________________
b ..qqq.. a
ppp ..has type.. relation
qqq ..has type.. relation
----


// https://ddot.it/on
.Built-in
[ddot.it]
----
has inverse ..has type.. relation
..has type.. symmetric relation
..has supertype.. related
..uri.. https://ddot.it/vocabulary/2026-07-20#has-inverse
----
// https://ddot.it/off


[[inverse-relations-on-the-fly]]
=== Syntax for Inverse Relations On The Fly
Given any relation `foo`, you can use `^foo` to state a triple like "the other way round".
Formally, **the `^` syntax only works as the first character in a relation name**. It's the same character used by the SPARQL query language for the same effect.

.Given / Inferred
[ddot.it]
----
a ..^foo.. b
_____________________________________
b ..foo.. a
foo ..has type.. relation
^foo ..has type.. relation
foo ..has inverse.. ^foo
^foo ..has inverse.. foo
----

And you can always give `^foo` a better <<label>>.








[[has-type]]
=== Relation `has type` / `has instance`
.Relation `has type`
`aaa ..has type.. Car` — `aaa` is an instance of the type `Car`.
The inverse is <<has-instance,`has instance`>>; the supertype is <<has-tag,`has tag`>>, because
typing is a refinement of tagging.

// https://ddot.it/on
[ddot.it]
----
has type ..has type.. relation
..has supertype.. has tag
..has inverse.. has instance
..uri.. https://ddot.it/vocabulary/2026-07-20#has-type
..has alias.. hasType
----
// https://ddot.it/off

.The `a` shortcut
In N3 (and other RDF syntaxes), the built-in `a` expresses typing, e.g. (`ex:Berlin`, `a`, `ex:City`).
To keep {dd} self-documenting, the canonical name is `has type`, so we write `Berlin ..has type.. City`.
But typing with just `a` is convenient, so `a` is declared to be <<replaces,replaced by>> `has type`:
an editor may substitute the one for the other, and a reasoner treats both as the same relation.

// https://ddot.it/on
.Built-in
[ddot.it]
----
a ..is replaced by.. has type
----
// https://ddot.it/off

[[has-instance]]
.Relation `has instance`
The inverse of <<has-type,`has type`>>: `Car ..has instance.. aaa` whenever
`aaa ..has type.. Car`.

Typing is a refinement of <<is-tag-of,tagging>>: `has instance` is a <<has-subtype,subtype>> of
`is tag of`. So `aaa ..has type.. Car` implies `aaa ..has tag.. Car`, which lets type-browsing and
tag-browsing share one user interface.

// https://ddot.it/on
[ddot.it]
----
has instance ..has type.. relation
..has supertype.. is tag of
..has inverse.. has type
..uri.. https://ddot.it/vocabulary/2026-07-20#has-instance
..has alias.. hasInstance
----
// https://ddot.it/off



[[has-subtype]]
=== Relation `has subtype` / `has supertype`
.Relation `has subtype`
Types assigned with <<has-type,`has type`>> are inherited along this relation.
The inverse is `has supertype`.

.Example
The type `Vehicle` has the more specialised type `Car`: `Vehicle ..has subtype.. Car`.

----
aaa ..has type.. Car
Vehicle ..has subtype.. Car
----
infers
----
aaa ..has type.. Vehicle
----
So if we know something is a _Car_, then it also must be a _Vehicle_.
It does not work the other way round.


// https://ddot.it/on
[ddot.it]
----
has subtype ..has type.. relation
..has type.. transitive relation
..has supertype.. has detail
..has inverse.. has supertype
..uri.. https://ddot.it/vocabulary/2026-07-20#has-subtype
..has alias.. subtype
----
// https://ddot.it/off

// https://ddot.it/on
.Relation `has supertype`
[ddot.it]
----
has supertype ..has type.. relation
..has type.. transitive relation
..has supertype.. has context
..has inverse.. has subtype
..uri.. https://ddot.it/vocabulary/2026-07-20#has-supertype
..has alias.. supertype
----
// https://ddot.it/off



.Cycles
If `has subtype` forms a cycle, all participants of the cycle are considered to be the same entity (<<same-as,`same as`>>).
This is exactly what the RDFS specification also states. This is the logicians' solution to "nothing is forbidden".

A linter should show such cycles, as they are rarely intentional.











[#top-level-relations]
== Top-Level Relations
The relation hierarchy has *two* roots, because {dd} relations do two different jobs:

<<related,`related`>>:: connects a <<type-thing,thing>> to a *thing*. Both ends have an identity of
their own, so the link is worth following in either direction.
<<property,`property`>>:: attaches a <<type-value,value>> to a thing. The value end has no identity
of its own; it merely describes the thing.

Every other relation in this document is a <<has-subtype,subtype>> of one of these two.

.Overview
[plantuml]
....
hide empty members
hide circle

' Each node is a "forward / inverse" pair. Convention: the FIRST (upper) name is the
' relation, the SECOND (lower) name its inverse. A single generalization edge encodes both,
' because a forward relation's supertype is always forward and an inverse's is always inverse.

class related <<symmetric>>
class property <<no inverse>>
note right of property
  Value-carrying relations.
  Subtypes: see "Relation property".
end note

' === identity / similarity branch (parent is symmetric, so no forward/inverse split)
class has_similar as "has similar" <<symmetric>>
class same_as as "same as" <<symmetric transitive>>
class alias as "is alias of /\nhas alias"
class replaces as "replaces /\nis replaced by" <<transitive>>

' === linking branch
class linking as "links to /\nis linked from"
class order as "has next /\nhas previous" <<transitive>>
class detail as "has detail /\nhas context"
class part as "has part /\nis part of" <<transitive>>
class subtype as "has subtype /\nhas supertype" <<transitive>>
class annotation as "annotates /\nhas annotation"
class tag as "is tag of /\nhas tag"
class instance as "has instance /\nhas type"

' === generalization = 'has supertype' (one edge = both directions)
related <|-- has_similar
has_similar <|-- same_as

linking <|-- annotation

tag <|-- instance
....

.Reading the diagram
- Each box holds a relation and its <<has-inverse,inverse>> as `forward / inverse`. The upper name is a `has subtype` of its parent's upper name; the lower name likewise on the inverse side. So one arrow `A <|-- B` states both _B.forward_ `has supertype` _A.forward_ and _B.inverse_ `has supertype` _A.inverse_.
- The symmetric relations (`related`, `has similar`, `same as`) are their own inverse, so they carry a single name.
- `property` is the second root and carries a single name for the opposite reason: its inverse exists but is not worth naming — see <<property>>.
- An arrow `A <|-- B` means: a statement using _B_ also holds for _A_ (via <<has-subtype,relation inheritance>>).
- `«symmetric»` and `«transitive»` mark relations of that <<type-relation,type>>; on a pair, the marker applies to both directions.
- Typing (`has instance` / `has type`) is deliberately a refinement of tagging, which is itself a refinement of annotation. This mirrors Fig. 4.5 of the source thesis (see <<has-instance>>).
- `has subtype` / `has supertype` refine `has detail` / `has context`: a subtype is a special kind of detail. The type hierarchy they build is shown in <<top-level-types,Top-Level Types>>.

[[related]]
=== Relation `related`
An undirected link connecting `foo` and `bar`, with no further claim about _how_ they are related.
The weakest link {dd} offers.
The root of all relations between <<type-thing,things>>.

// https://ddot.it/on
[ddot.it]
----
related ..has type.. relation
..has type.. symmetric relation
..uri.. https://ddot.it/vocabulary/2026-07-20#related
..has alias.. is related to
..has alias.. hasRelated
----
// https://ddot.it/off


[[property]]
=== Relation `property`
`foo ..property.. bar` — `bar` is a <<type-value,value>> that describes `foo`.
The weakest such statement {dd} offers, and the root of all value-carrying relations.

Because the object is a value, stating a `property` also tells us what kind of entity sits on each
end — this is how {dd} recovers the <<type-thing,thing>> / <<type-value,value>> distinction that
its single string datatype cannot express:

.Given / Inferred
[ddot.it]
----
aaa ..ppp.. vvv
ppp ..has supertype.. property
___________________________________
aaa ..has type.. thing
vvv ..has type.. value
----

.No named inverse
`property` and its subtypes deliberately have **no** <<has-inverse,`has inverse`>>.
The inverse direction is well defined — "which entities carry this value?" — but the value end is
not an entity you navigate _from_, so naming a relation for it would only invite people to model
values as things.

Where the inverse is genuinely needed, the <<inverse-relations-on-the-fly,`^` syntax>> supplies it
without a name: `^property`, `^label`, `^grade` always exist and can be given a <<label>> locally.

// https://ddot.it/on
[ddot.it]
----
property ..has type.. relation
..uri.. https://ddot.it/vocabulary/2026-07-20#property
..has alias.. has property
..has alias.. hasProperty
----
// https://ddot.it/off

NOTE: A <<identifying-relation,`identifying relation`>> is always a subtype of `property`: it carries
a value that happens to pin down its subject.

== Identity: Same or Different?
Some core relations.

[[has-similar]]
=== Relation `has similar`
`foo` and `bar` are similar, without any claim that they are the same.
Weaker than <<same-as,`same as`>>, stronger than <<related,`related`>>.

// https://ddot.it/on
[ddot.it]
----
has similar ..has type.. relation
..has type.. symmetric relation
..has supertype.. related
..uri.. https://ddot.it/vocabulary/2026-07-20#has-similar
..has alias.. is similar to
..has alias.. hasSimilar
----
// https://ddot.it/off

`has similar` is symmetric but *not* transitive.
From `a ..has similar.. b` and `b ..has similar.. c` nothing follows about `a` and `c`.
That is what makes it the safe target for importing fuzzy links such as `skos:closeMatch` or
WordNet's _similar to_ — see link:ddot-it-relations.adoc#standards[the alignment tables].


[[same-as]]
=== Relation `same as`
`foo` and `bar` refer to the same concept.
Neither one is the main name — compare <<is-alias-of,`is alias of`>>, which does distinguish.

// https://ddot.it/on
[ddot.it]
----

..has type.. symmetric relation
..has type.. transitive relation
..has supertype.. has similar

[[replaces]]
=== Relations `is replaced by` / `replaces`
`foo ..replaces.. bar` — `foo` supersedes `bar`.
Both remain distinct entities; use <<same-as,`same as`>> if they are in fact the same thing.

== Hierarchies

[[has-detail]]
=== Relations `has detail` and `has context`
`foo ..has detail.. bar` — `bar` elaborates or refines `foo`.
Read the other way, `foo` is the context in which `bar` makes sense.

// https://ddot.it/on
.Built-in
[ddot.it]
----
has detail ..has type.. relation
..has supertype.. links to
..has inverse.. has context
..uri.. https://ddot.it/vocabulary/2026-07-20#has-detail
..has alias.. hasDetail

has context ..has type.. relation
..has supertype.. is linked from
..has inverse.. has detail
..uri.. https://ddot.it/vocabulary/2026-07-20#has-context
..has alias.. hasContext
----
// https://ddot.it/off

The relations `has detail`/`has context` are *not* transitive, unlike <<has-part,`has part`>> below, which is a more
specific relation. A detail of a detail is not automatically a detail of the whole.


[[has-part]]
=== Relations `has part` and `is part of`
`foo ..has part.. bar` — `bar` is a component of `foo`.
Both directions are transitive: a part of a part is a part of the whole.

// https://ddot.it/on
[ddot.it]
----
has part ..has type.. relation
..has type.. transitive relation
..has supertype.. has detail
..has inverse.. is part of
..uri.. https://ddot.it/vocabulary/2026-07-20#has-part
..has alias.. hasPart

is part of ..has type.. relation
..has type.. transitive relation
..has supertype.. has context
..has inverse.. has part
..uri.. https://ddot.it/vocabulary/2026-07-20#is-part-of
..has alias.. isPartOf
----
// https://ddot.it/off

.Tags propagate to parts
A tag on a whole applies to each of its parts:

.Given / Inferred
[ddot.it]
----
aaaPart ..is part of.. bbbWhole
bbbWhole ..has tag.. cccTag
___________________________________
aaaPart ..has tag.. cccTag
----


.Example
----
Engine ..is part of.. Car
Car ..has tag.. mechanical
__________________________
Engine ..has tag.. mechanical
----








== Going Meta

[[annotates]]
=== Relations `has annotation` / `annotates`
`bar ..annotates.. foo` — `bar` is a remark, comment or note *about* `foo`.
The annotation is a first-class entity, so it can itself be annotated, tagged or typed.

// https://ddot.it/on
[ddot.it]
----
annotates ..has type.. relation
..has supertype.. links to
..has inverse.. has annotation
..uri.. https://ddot.it/vocabulary/2026-07-20#annotates
..has alias.. has annotation member
..has alias.. hasAnnotationMember

has annotation ..has type.. relation
..has supertype.. is linked from
..has inverse.. annotates
..uri.. https://ddot.it/vocabulary/2026-07-20#has-annotation
..has alias.. hasAnnotation
----
// https://ddot.it/off

TIP: Annotating a *triple* rather than an entity is what the `,,` meta part is for.
See link:ddot-it-parse.adoc#parsing[parsing].





[[has-tag]]
=== Relation `has tag` / `is tag of`
.Relation `has tag`
`foo` has the tag `bar`.
A tag is usually a single term. Sometimes multiple words are also used.

// https://ddot.it/on
[ddot.it]
----
has tag ..has type.. relation
..has supertype.. has annotation
..has inverse.. is tag of
..uri.. https://ddot.it/vocabulary/2026-07-20#has-tag
..has alias.. tag
----
// https://ddot.it/off

Tags are *not* transitive. A tag on a tag says nothing about the tagged entity.

[[is-tag-of]]
.Relation `is tag of`
The inverse of <<has-tag,`has tag`>>: `bar ..is tag of.. foo` whenever `foo ..has tag.. bar`.
Declared separately so that the tag side of the pair has a name and a URI of its own.

// https://ddot.it/on
[ddot.it]
----
is tag of ..has type.. relation
..has supertype.. annotates
..has inverse.. has tag
..uri.. https://ddot.it/vocabulary/2026-07-20#is-tag-of
..has alias.. has tag member
..has alias.. hasTagMember
----
// https://ddot.it/off



[[content-management-relations]]
== Content Management Relations


[[label]]
=== Relation `label`
`foo ..label.. bar` sets the visible label of `foo` to `bar`.
The semantic layer therefore gives every node an _id_ and a _label_, the latter defaulting to the
_id_ string. Tools that display the knowledge graph show the label and hide the relabelled id.
Outside a triple relation, `label` has no defined semantics — using labels happens in higher layers
and tools.

// https://ddot.it/on
[ddot.it]
----
label ..has type.. relation
..has supertype.. property
..uri.. https://ddot.it/vocabulary/2026-07-20#label
..has alias.. has label
----
// https://ddot.it/off


NOTE: In previous versions of {dd}, this was modelled as a command (`!!label`).



[[text]]
=== Relation `text`
This relation is one of the relations built into {dd} parsing.
It carries the free text of a `,,` link:ddot-it-parse.adoc#parsing[meta] that holds no triple (`MetaTextInline` / `MetaTextBlock`).
Or assigns arbitrary content to a subject.

When parsing link:ddot-it-parse.adoc#parsing[meta-text], as in `s..p..o,, meta-text`, this is reported on the triple event layer as (`meta: [{"r":"text","o":"meta-text"}]`).

// https://ddot.it/on
[ddot.it]
----
text ..has type.. relation
..has supertype.. property
..uri.. https://ddot.it/vocabulary/2026-07-20#text
..has alias.. has text
..has alias.. has content
----
// https://ddot.it/off



[[semantic-web]]
== Linking with the Semantic Web
{ddd} should be compatible with semantic web / linked open data standards.
The triple structure fits exactly, and even the triple-meta parts map to upcoming RDF 1.2 specs (see https://www.w3.org/TR/rdf12-primer/[Primer] or https://www.w3.org/TR/rdf12-concepts/[Spec]).
The "base layer" of these standards, The _Resource Description Framework (RDF)_, mandates that resource identifiers are URIs.
For that reason, we **give every {dd} relation a URI** via {dd} `uri`.

[[uri]]
=== Relation `uri`
// https://ddot.it/on
.Built-in
[ddot.it]
----
uri ..has type.. relation
..has supertype.. property
..uri.. https://ddot.it/vocabulary/2026-07-20#uri
----
// https://ddot.it/off

If an entity has several URIs, all of them denote the same entity.

[[prefix]]
=== Relation `prefix`
// https://ddot.it/on
.Built-in
[ddot.it]
----
prefix ..has type.. relation
..has supertype.. property
..uri.. https://ddot.it/vocabulary/2026-07-20#prefix
----
// https://ddot.it/off

Additionally, because URIs are visually quite ugly and have a repetitive part, it's common practice in most syntaxes to abbreviate the reoccurring URI prefix. {ddd} does the same.

.Effect
- For any string starting with a sequence `foo:bar` in
** subject (`foo:bar ..y.. z`)
** relation (`x ..foo:bar.. z`), or
** object (`x ..y.. foo:bar`),
- where we also have the triple `foo .. prefix .. baz`,
- we infer a similar string with the prefix **resolved** into its **namespace**
** subject (`bazbar ..y.. z`)
** relation (`x ..bazbar.. z`), or
** object (`x ..y.. bazbar`).

In practice, `baz` is usually something like `https://example.com/ns/v3/`.

.The {dd} Namespace
We also state as a built-in:

// https://ddot.it/on
.Built-in
[ddot.it]
----
ddot ..prefix.. https://ddot.it/vocabulary/2026-07-20#
----
// https://ddot.it/off



[[provenance]]
== Provenance
In this section we define some common relations to be used in the link:ddot-it-parse.adoc#information_model[meta] part of a triple (after the `,,` marker).
All of them take a <<type-value,value>> as object; all dates and times are ISO 8601 strings.

[[source-uri]]
=== Relation `source uri`
The file or web resource a triple was collected from — maybe only for debugging, maybe always.
The URI should name the source file and should locate the source lines in the `#` fragment,
e.g. `+file:///home/me/notes.adoc#L12-L14+`.

// https://ddot.it/on
[ddot.it]

[[grade]]
=== Relation `grade`
How much a triple can be trusted. The object is one of `unreviewed`, `reviewed` or `manual`.

An *unreviewed* triple is a tool's guess and should be treated as disposable.
A tool that re-runs its matcher is expected to drop the `..grade.. unreviewed` triples it previously emitted.
Never store an author's intent as an auto-link.

// https://ddot.it/on
[ddot.it]
----
grade ..has type.. relation
..has supertype.. property
..uri.. https://ddot.it/vocabulary/2026-07-20#grade

unreviewed ..has type.. grade value
..uri.. https://ddot.it/vocabulary/2026-07-20#unreviewed
reviewed ..has type.. grade value
..uri.. https://ddot.it/vocabulary/2026-07-20#reviewed
manual ..has type.. grade value
..uri.. https://ddot.it/vocabulary/2026-07-20#manual

grade value ..has type.. type
..has supertype.. value
..uri.. https://ddot.it/vocabulary/2026-07-20#grade-value
----
// https://ddot.it/off

== Versioning
This vocabulary is versioned independently of the {dd} syntax specification.

.Version number
The title carries a semantic version (currently *1.1.0*):

- *Major* — a built-in was removed or its meaning narrowed, so previously valid data may now be wrong.
- *Minor* — built-ins were added, or aliases and supertypes were added without invalidating existing data.
- *Patch* — wording, examples and typo fixes only; no triple changed.

.Namespace date
Every built-in URI lives in a dated namespace, currently
`+https://ddot.it/vocabulary/2026-07-20#+` (see <<prefix,`prefix`>>).
The date changes only on a *major* version, so minor and patch releases keep every existing URI
resolvable. Consumers should therefore pin the namespace, not the version number.

.Changes
Because a minor release only ever *adds* built-ins, a consumer that ignores relations it does not
know stays correct across minor upgrades. The per-release list of changes is kept in the
link:../CHANGELOG.md[{ddd} changelog].

NOTE: This is a property of the *release policy*, not the same thing as the <<monotonicity,monotonicity>>
of the language itself. Both point the same way — nothing is ever taken back — but a major release
_may_ remove a built-in, whereas monotonicity holds for every version of {dd}.
